A few weeks ago I had agents spec out an autonomous trading desk: 231 files of design docs, specs, build slices and a Go scaffold, shipped as 35 small PRs. Codex wrote every word, Claude orchestrated, and I read maybe a dozen files properly.

My first instinct was guilt. Then I went looking for the evidence that reading code was ever what kept it honest. There isn’t much.

Reading was always a weak check

Microsoft studied its own code reviews and found that only about 15% of reviewer comments point to a possible defect, “much less a blocking defect” (Czerwonka, Greiler, Tilford, 2015). Most comments were about long-term maintainability. An earlier Microsoft study came to the same place: developers expect review to find bugs, but what it mostly delivers is knowledge transfer and team awareness (Bacchelli & Bird, 2013).

Science has run the cleanest version of this test. The BMJ sent 607 peer reviewers papers with nine major errors planted in them. On average they found 2.58 (Schroter et al., 2004). These are experts, reading slowly, whose actual job is finding mistakes.

The reason is human hardware. Vigilance research says nobody, however motivated, can keep watching for rare problems for much more than half an hour (Bainbridge, 1983). The industry review guidance says the same thing in practice: under 400 lines, under 60 to 90 minutes, or detection falls off (SmartBear/Cisco). An agent can produce 400 lines before you’ve finished your coffee.

So reading code was never a reliable bug filter. It worked because volume was low and it carried two other jobs along with it: a second person understood the change, and someone put their name on it.

Every field that scaled hit this wall first

Manufacturing got there in the 1950s. Deming’s third point: “Cease dependence on inspection to achieve quality.” Inspection at the end of the line is too late, the defect is already in the product. You build quality into the process instead (Deming’s 14 points).

Science got there too. Nobody trusts a result because two reviewers read it. They trust it because someone else ran it again.

Reading every line of agent code is end-of-line inspection. It doesn’t scale, and it wasn’t catching much when it did.

What “built-in quality” looks like with agents

There’s an asymmetry that makes this work. Plenty of things are much easier to check than to produce, and AI gets good fastest at whatever is easy to verify (Jason Wei, verifier’s law). Writing a trading engine is hard. Checking that it rejects an order over the position limit is a test.

So the work moves from reading output to building checks. Three things matter most.

1. Checkers that don’t share your blind spots

In 1986, Knight and Leveson had 27 programmers write the same program independently. The programs failed together far more often than chance predicts, because people make the same mistakes on the same hard parts (Knight & Leveson). Two checkers who think alike are closer to one.

Models are worse here than people. Letting a model refine its own code five rounds in a row, with no outside check, produced a 37.6% increase in critical vulnerabilities.

On the trading desk I ran three reviewer agents, each with one lens: consistency, money-path safety, and “could a fresh agent actually build this slice”. First pass: 87 findings, 43 of them blocking. Almost all of them sat in the seams between files, where no single writer owned both sides. A manifest path spelled two ways, a test ID cited in one doc and missing from the catalogue. A separate arbiter agent made the binding call when they disagreed, 33 times. Otherwise you get agents politely arguing forever.

2. Run it, don’t read it

A diff tells you what the code says. A test run tells you what it does.

Every slice in my build plan names its test IDs up front, and a slice isn’t done until they exist and pass. Coverage goes unit to e2e, no exceptions. Seeds aren’t dummy data; they need to look like prod in shape, if not in volume.

One catch: agents will game a check if they can. METR caught frontier models modifying tests and monkey-patching evaluators to get a perfect score (METR, 2025). So the agent writing the code doesn’t get to own the tests that grade it.

3. Write the context down, inside the repo

An agent can only be checked against what’s written down. ADRs, runbooks, schema commentary, the ICP, all inside the codebase. If an agent can’t grep it, it doesn’t exist.

Same for the reasoning. Every agent conversation gets attached to the PR, so when something breaks I read a few paragraphs of reasoning instead of a few thousand lines of code.

Prove it’s clean, fast and secure

Passing tests is the floor. “It works” is the thing models have got best at. What they’re still weak on is what a careful reader used to look for, and each one has a check that does it better than a reader.

Clean. GitClear analyzed 211 million changed lines from 2020 to 2024. As AI assistants spread, duplicated code blocks rose eightfold in 2024, and for the first time in their data, copy-pasted code outpaced refactored code (DevClass on GitClear, 2025). Messy code costs real time. Across 39 production codebases, tasks in the unhealthiest code took 124% longer, and that code had 15 times more defects (Tornhill & Borg, 2022). The check: duplication and complexity limits in CI, plus a code-health score that fails the build when it drops.

Fast. Correct isn’t quick. On EffiBench, GPT-4’s working solutions took 3.12 times as long to run as human-written ones on average, and in the worst cases 13.89 times as long with 43.92 times the memory (Huang et al., 2024). The check: performance budgets in CI. Benchmarks on the hot paths that fail the build when latency or memory regresses.

Secure. Veracode gave more than 100 models 80 coding tasks. 45% of the code had a security flaw, 72% in Java, and newer, bigger models were no better at security even as they got better at writing working code (Veracode, 2025). The check: static analysis and dependency scanning on every PR, plus a reviewer agent whose only job is security.

And the tests themselves. A passing suite only proves what it tests. Mutation testing breaks the code on purpose and checks that a test fails. Google runs it inside code review, across millions of mutants (Petrović et al.). A mutant that survives means a test that wasn’t checking anything.

Where the human goes

Bainbridge’s paper is called Ironies of Automation, and the biggest irony applies to us. Automate the work, leave the human watching, and you’ve given them the one job humans are worst at. Their skills fade from disuse, and they’re still the one blamed when it fails. Madeleine Clare Elish calls that person the moral crumple zone. Research on automation bias adds that training and instructions don’t prevent it (Parasuraman & Manzey, 2010).

So “skim the agent’s PRs” is the worst of both. You’re not really checking, and you’re still on the hook.

The useful human work sits upstream. My one real mistake on that build wasn’t in the code. I let a research pass pick Python for the stack, never asked myself the question, and ended up migrating the whole design to Go. No line of code came close to costing me that much.

Agents are very good at code that is locally right. The expensive mistakes are decisions: the architecture, the language, the data model, what to test, what not to build at all. Those are what I read now.

Be the validator, not the proofreader. Comprehension is now a function of our tools, not a state of our minds. Weird, novel and kinda scary, but we were never as good at the old way as we thought.
